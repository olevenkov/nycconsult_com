Cloud landing zone planning checklist

A landing zone is the shared foundation for cloud workloads. Its design should make identity, connectivity, security, and operations understandable before teams depend on it.

1. Define account and environment boundaries

Decide how accounts, subscriptions, or projects will separate production, non-production, shared services, and teams. Document who can create them and how ownership changes are handled.

2. Establish identity and access patterns

  • Integrate workforce identity and define role-based access.
  • Prefer short-lived, workload-specific credentials over shared long-lived secrets.
  • Document privileged access, break-glass use, and access review ownership.

3. Design network connectivity deliberately

Map required paths between cloud workloads, corporate networks, internet services, and other environments. Clarify DNS, ingress and egress controls, segmentation, and responsibility for network changes.

4. Make security policy and logging repeatable

  • Set baseline encryption, key management, and resource policy expectations.
  • Centralize audit logs and security findings with clear access and retention owners.
  • Use policy-as-code for controls that can be tested reliably.
  • Define how exceptions are approved, recorded, and revisited.

5. Provision through infrastructure as code

Use reviewed, version-controlled templates for shared foundation components. Include testing, change approval, drift detection, and a documented path for safe updates.

6. Assign operational ownership

For each shared service, identify the owner, support path, monitoring, recovery expectations, and change process. A landing zone is an operating model as well as a technical architecture.

Before workloads onboard

Confirm that a representative workload can be provisioned, deployed, observed, secured, and recovered using the intended patterns. Record unresolved risks and assign owners instead of treating a checklist as proof of compliance.
